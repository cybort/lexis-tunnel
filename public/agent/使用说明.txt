词隙客户端 4.1.0（协议 lexis-hctr2-bb-k-v4s）

显式回退 frame.dte="bb-k-v4" 时与 4.0.0 相同（方案 K，协议名 lexis-hctr2-bb-k-v4）。帧词模型公开，和会话密钥无关。密钥参与密文以下的尾部：收端用同一条 AES-CTR 流重封，词串必须逐词一致。重封对得上说明这把密钥能生成这条尾，不能证明帧来自对端。持有候选会话密钥的人可以做这次检查。蜜文路径不做重封，错钥仍得到格式合法的视图。蜜文挡的是长期私钥和口令，不挡已经拿到候选会话密钥的人。没有尾部密钥的观察者，分不开这条尾和随机数；这不是超出公开词模型的单独字节分布证明。

握手报文的布局和长度与 3.0.x 相同，线上没有新的字段。默认 frame.dteCheck=true 时，frame.dte 会绑进密钥确认的 transcript，和 3.0.x 的确认对不上。因此默认不能和 3.0.x 互通：内网端密钥确认失败后关掉连接；闸门只回一次应答，放出半开名额，连接静默到握手超时，不再多写一个字节。要和仍跑 3.0.x 的一端互通，这一端必须同时设 frame.dte="rans-v3" 且 frame.dteCheck=false。只改 dte 不够。两端都是 4.x 且不是 bb-k-v4s 混用时，仍建议保持 dteCheck=true。

frame.dte 可选值：
  "bb-k-v4s"（4.1.0 默认；方案 K + 共用允许词表 + 会话打乱，见 docs/design/frame-v4s-session-vocab.md）
  "bb-k-v4"（4.0.0 默认，方案 K，现为显式回退；与 bb-k-v4s 不互通）
  "bb-c8-v4"（A1，不推荐：单词篡改实测 19/6000 仍被接受且明文不变。这不是安全性证明。同一测量里 bb-k-v4 是 0/6000）
  "bb-v4"（A0：末几个尾词可被替换而仍能解开，明文不变）
  "rans-v3"（数据帧与 3.0.x 相同；和 3.0.x 握手还要 frame.dteCheck=false）
  "bb-ou-v4"、"bb-ouc8-v4"、"bb-ouc8r-v4"、"dfa-v4"（实验，不建议用于真实流量）
两端 frame.dte 必须相同，线上不协商，未知值拒绝启动。frame.dteCheck 两端也必须相同。检查打开时，dte 不一致在握手阶段失败，不是可读的帧错误。检查关闭时，握手能完成，首个数据帧再谈完整性；不同 dte 的数据帧基本解不开（bb-k-v4 发出的帧 bb-v4 能解，反方向不行；bb-v4 与 bb-c8-v4 之间大约 0.5% 碰巧能解）。细节在仓库的 docs/design/frame-v4-k-tail.md，安装包里没有这份文档。

4.1.0 默认 frame.dte 改为 "bb-k-v4s"（协议 lexis-hctr2-bb-k-v4s）。编码仍是方案 K（满射区间编码 + 带钥规范尾），只换词表来源：产品内带一份全体会话共用的允许词表（FrequencyWords 清洗后、构建时去掉一小批指定整词，其余 46,701 词全部保留，包标识 fw50k-all-d1-gf，由 dte 取值隐含），会话密钥只在频次相近（相差不超过 1.5 倍、每组最多 256 个）的组内打乱词序，每个会话的模型都含全部允许词；同组词频次相同，打乱不改变任何词的出现概率。数据帧和 finish 用握手后的会话密钥派生词序，hello/闸门回包用令牌与闸门公钥派生词序，两者都建在同一份允许词表上。
与现网 bb-k-v4 不互通：两端要一起升级，或者两端都显式写 frame.dte="bb-k-v4"。混用时在握手阶段失败关闭：bb-k-v4s 一端与任何其它 dte 一端的 hello 词表不同，闸门认不出 hello，按坏令牌处理（不回任何字节，静默到握手超时），edge 等不到回包超时失败；这与 frame.dteCheck 开关无关，关掉 dteCheck 也不能让两者握手。不要靠关 dteCheck 来“兼容”。

以下沿用 3.0.4 的系统接管说明（半开、用户态栈、RST、IPv6）。安装包本身是 4.1.0，默认帧是 bb-k-v4s（方案 K + 共用允许词表），不是这一段标题里的 rans-v3。

这一版和 2.x、1.8.0 及更早的所有版本都对不上，两端（edge 和 gate）必须同时升级到 3.0.x。帧改成 HCTR2 宽块置换加语料词编码，握手的临时密钥是 X25519（Elligator2 编码），长期身份密钥也从 P-256 换成了 X25519（32 字节）。旧的 P-256 身份文件不能自动迁移，加载时会报错，两端都要重新生成身份并互相交换新公钥。握手口令也必须重新生成（见下）。新旧进程连握手都过不了：闸门对旧版 hello 一律静默丢弃，等到握手超时才断开，不会回任何报错。线上没有版本字节（加了就是指纹），所以版本不一致只表现为“握手超时”。时钟窗仍是 300 秒、左右各 120 秒。

转发正文和控制台是同一套词表。两端用 X25519 长期公钥和临时密钥做 DH（Noise NK 式，闸门长期公钥参与 hello 加密），会话密钥用 Argon2id。常驻进程用自己配置里的内存、迭代和并行，不采用对端报上来的更高开销。伪造问候要先过握手口令。口令写在 link.token，两端相同，估算熵必须不少于 128 bit，否则进程拒绝启动；请用 node lexis-agent.mjs --gen-token 生成，不要手写。它在 Argon2 之前校验，不是词表密钥。问候的时间窗是 300 秒。时钟慢或快时，上一窗只在新窗的前 120 秒还接受，下一窗只在当前窗的最后 120 秒接受。更远的窗仍然拒绝。过期的问候和同一个时间窗里的重放都会被拒绝。同一个节点或同一个地址在一个时间窗里不能占满全部名额。派生密钥的线程如果出错或超时，下一次握手会再拉起一个。

正文、填充和 16 字节助记码放进 HCTR2，再按这把会话密钥打乱过的英文词序写成词。线上没有版本字节。持有候选会话密钥的人，可以用词序重编码确认这把密钥：对的密钥几乎总能重编码回去，错误密钥大约只有 2% 到 3% 碰巧通过。蜜文挡的是对长期私钥和口令的暴力猜测，不挡已经拿到候选会话密钥的人。会话密钥来自临时密钥，拿长期私钥和转录推不回去。握手确认用临时共享秘密来算，不是公开的转录标记。闸门校验失败一律静默丢掉。明文第一个字节仍表示原文或 zstd。小帧默认少填充，很短的单发帧会超过 5 倍；小帧策略写成 honey 时，填充占比更接近错误密钥解出来的样子，两端可以各写各的。计数器跨换钥连续递增。换钥载荷是 16 字节随机数再加 4 字节时间窗。心跳如果连续三个周期没有收到对端，这条会话会关掉。长期私钥可以封成系数：任意一句口令都解开一把合法的 X25519 种子，程序里没有「这句口令是备用」的判断。封面系数不再决定线上帧写出来的句子。

外层只负责把头和协议走完，方便过 CDN：
- tcp：一行一句词表
- tls：同一句词表走在 TLS 应用数据里。正式部署请换成自己的证书，并打开校验。tlsVerify 为 false 时进程会警告
- ws / wss：一条 WebSocket 文本消息就是一句词表，路径默认 /lexis。CDN 若自己终结 TLS，源站听 ws，客户端连 wss，并填 CDN 的主机名

身份写在 identity。peers 里放要加入的节点，公钥必须对上。没有封存时，导出的配置带本机私钥，不要外传。封存以后，配置和侧车都不写私钥标量，也不写系数。系数只在旁边的 lexis.seal.json，里面没有公钥、没有指纹。口令放在环境变量 LEXIS_PASSPHRASE，或同目录的 lexis.passphrase。常驻进程用同一条求值解开，不会拿结果去对配置里的公钥，也不会把标量写回磁盘。口令不对会得到另一把合法私钥，对端会说绑定不一致，不会说口令错误。封存的 Argon2id 是 65536 KiB、3 次迭代，不吃握手那一档 16384 KiB 的上限。同时拿到封存文件和这份公钥的人，仍可以离线试口令，只是更慢。改名单不用重启：摘掉的节点，会话会关掉。

一条会话上可以开多路。打开命令是 `tcp 主机 端口`、`udp 主机 端口`、`relay 节点 tcp 主机 端口`，或 `expose 服务名`。中继默认关闭，出口也默认关闭。想让某个节点借本机中继，把 relay 设为 true。想让它把本机当出口，把 exit 设为 true。targets 写了就只允许那些目标，空着不限制。暴露不能经中继打开。跳数超过 4 就拒绝。把流送回上一跳也会拒绝。某一路读得慢，只堵住这一路，不会拆掉整条会话。本机这一侧也会停下来等信用，不会无限读进内存。

NAT 后面的机器用边缘角色连出去。配置里的 role 必须写成 edge 或 gate。缺了角色不再当成边缘，进程拒绝启动，也只有 edge 会去保持到对端的连接。exposes 里写服务名、本机 host:port，以及允许访问的节点名或编号。公网闸门用 reverses 在本地听一个端口，从已经连进来的会话反向打开同名服务。也可以访问「节点名:服务名」。没有那条会话时，会说没有来自该节点的会话。没有打开 link.allowLan 时，反向入口即使写成 0.0.0.0 也只绑回环，并且计入连接数上限。断线后边缘角色会退避重连。状态页默认只绑回环，这时 /metrics 和页面不需要口令。statusHost 离开回环时，要有 statusToken，请求带 Authorization: Bearer 或 ?token=。口令是空的又没有允许局域网，状态页改绑回环。/health 一直公开，而且只回答是否活着。

要听 tls 或 wss，把自己的证书和私钥放到程序旁边，命名为 lexis-tls.crt 和 lexis-tls.key。两边都没有时，如果本机有 openssl，进程会在旁边生成一把，只给这一台用，不要把那把私钥分发出去。

SOCKS 接受 CONNECT 和 UDP ASSOCIATE，UDP 可以是 IPv6。http 入站是 HTTP 代理，支持 CONNECT 和绝对地址的普通请求，认证跟 SOCKS 用同一对用户名密码。同一条连接上的每一个请求都会单独重写：代理认证不会带到目标，Host 必须和绝对地址一致，Content-Length 和 Transfer-Encoding 写在一起会直接拒绝，不会转发出去。客户端写了 Connection: close，或者 HTTP/1.0 没有 keep-alive，这一次响应后会关掉到客户端的连接。HEAD、204、304 没有正文，不会干等到空闲超时。1xx 会转给客户端，然后继续读真正的响应。没有长度、也不是分块、一直读到连接关闭的响应，末尾不足 16 KiB 的那段也会送完。socksAuth 的用户名和密码都填了才认证，留空就不认证。SOCKS UDP ASSOCIATE 的控制连接另有空闲 link.udpAssociateIdleMs，默认 120000 毫秒，只按合法的 UDP 活动续命；控制连接自己没数据，不再拆掉还在收发的关联。这一项没有把重连门槛当成已经通过。

固定端口：进程监听配置里的端口。SOCKS 和 HTTP 给本机程序当代理；TCP 入站按目标转发；tunnel 入站做词表握手，然后接受上面的打开命令。
系统接管：进程仍常驻，并写出平台脚本。Linux 在有 root 时写 redirect、tproxy 或虚拟网卡的规则。redirect 是混合方式：本机 TCP 由 iptables nat OUTPUT 的 REDIRECT 转回透明端口，本机 UDP 走 TPROXY 进同一端口的透明 UDP 监听，UDP 不再直连。tproxy 的 TCP 和 UDP 都走 TPROXY，同时写 PREROUTING 和 OUTPUT。TPROXY 优先用原生 nft（自有表 ip lexis_tproxy），没有时用 iptables 的 TPROXY。redirect 和 tproxy 启动前先检查：TPROXY 可用（nft tproxy 或 iptables TPROXY），lexis-sockopt.node 能开透明 UDP 监听（IP_TRANSPARENT），tproxy 还要能开透明 TCP 监听，redirect 还要有 iptables 的 nat REDIRECT。缺任何一项就拒绝系统接管：不装任何会改流量的规则（IPv6 规则也不装），状态页写明原因；虚拟网卡可用时提示改用虚拟网卡，也不可用时写明这台机器无法系统接管。不会退回只拦 TCP、让 UDP 直连，也不会改成只劫持 DNS。tproxy 的透明监听失败时不再改听 redirect。换 method 重新执行时，只删本程序给其它方法装过的规则（数值按当前配置）。本进程的每一条出站，包括连对端的隧道外层，先打 fwmark，规则碰到这个标记就放行。旁路标记是配置里的 mark，转进本机监听的是另一个标记，两个不能用同一个。私网、运营商级 NAT、组播和对端的 IPv4 地址不接管。IPv6 这一版还没有单独的监听。虚拟网卡 lexis0 的默认路由只接公网；私网和对端地址仍走原来的路由。redirect、tproxy、tun 都只处理 IPv4：linux.ipv6 默认是 "block"，三种方法下公网 IPv6 都被设为不可达（回环、链路本地 fe80::/10、ULA fc00::/7、组播、对端的 IPv6 字面量地址，以及带旁路标记 mark 的本进程出站不受影响），应用会回落到 IPv4，避免 IPv6 绕过隧道直连；IPv6 不经隧道。设为 "off" 时不处理 IPv6，IPv6 直接走本机网络、不经隧道，并撤掉本程序先前加的这些 IPv6 规则（只删这些，优先级、前缀或表不同的规则不动）。ICMP（含 ping）在 tun 下不转发，也不会伪造回复。用户态栈仍是词隙自己的，不是 gVisor：SYN|ACK 带 MSS 选项（tun.mtu 减 40，默认 1460），发送段长取它和对端 SYN 里 MSS 的较小值（对端没带时按 536）；未确认的段按 RTO 定时重发；乱序段按上限缓存多段（见下面的 tun 一节），对端窗口是 0 时停发。本机 DNS（Linux 系统接管）：redirect、tproxy、虚拟网卡三种方法都一样，也不管 linux.dnsRedirect 怎么设：进程先在 127.0.0.1 和 ::1 起本机 DNS 服务（UDP 和 TCP 同一端口，linux.dnsPort 默认 0 表示自动挑空闲端口，也可手填；这台机器没有 IPv6 时只听 127.0.0.1），起来以后才写规则；规则把本机发出的所有 TCP/UDP 53 都劫持到这个服务（IPv4 用 nft 自有表 ip lexis_dns，没有 nft 时用 iptables nat 链 LEXIS_DNS；IPv6 用 ip6 lexis_dns 或 ip6tables nat 链 LEXIS_DNS），写死 1.1.1.1、8.8.8.8 的程序和私网里的 DNS 服务器（路由器 192.168.x.1、10/8、172.16/12、ULA fc00::/7、链路本地）都算在内：53 的劫持在 nat 里排在所有私网旁路之前（nft 优先级 -110，iptables 链排 nat OUTPUT 第一条），53 不走私网旁路。只有发往回环（127.0.0.0/8、::1，例如 systemd-resolved 的 127.0.0.53 存根，它往上游发的查询照样被劫持）和带旁路标记 mark 的本进程出站不劫持。TCP DNS 也一样接管。linux.dnsRedirect 不是 false（默认）时：A 记录给 198.18.0.0/15 里的一个假地址，AAAA 回空的 NOERROR，其它类型（MX、TXT、PTR 等）转给上游。linux.dnsRedirect=false 时：不回假地址，全部查询（A 也一样）由本机服务转给上游，应用拿到真实地址。上游是 linux.dnsUpstream（默认 1.1.1.1:53，只收 IPv4 地址），这条转发和别的连接一样按规则走：默认经隧道，不直连；要让内网域名走路由器，把 dnsUpstream 设成路由器地址（规则里私网是直连时，这条转发带旁路标记直连路由器）。被劫持的查询本来要发给哪台服务器，UDP 在 nat 之后读不到，所以不会再发给原来的解析器。服务起不来（例如手填的端口被占、::1 听不上）或 53 劫持装不上（nft 和 iptables 的 nat 都不可用，IPv6 也算）时，拒绝系统接管，不装规则，状态页写明原因；规则装到一半失败（任何一条命令出错、脚本被打断或超时），脚本撤掉本程序已经装的全部规则（含 IPv6 规则和 53 劫持）再拒绝接管，不会出现其它规则装好了、只有 53 直连的半装状态。接管以后进程若退出，劫持规则还在，53 查询在本机就失败，不会回落直连。状态页和 /metrics 显示服务是否在听、地址端口、53 是否已劫持（IPv4、IPv6）、是否回假地址、dnsRedirect 的配置值和失败原因（lexis_dns_local_listening、lexis_dns_hijacked、lexis_dns_hijacked_ipv6、lexis_dns_fakeip、lexis_dns_local_queries_total、lexis_dns_hijack_total）；改了 dnsRedirect 要重启才生效，状态页会提示。假地址只存在于本机，拨号前映射回域名，这样 GEOSITE 仍看得到名字，也绝不会去连 198.18。标记由本机模块设置，连接由 Node 发起，不再在主线程里同步解析和等待。没有 root 时规则只留在文件里；redirect 和 tproxy 缺上面任何一项能力时拒绝接管；内核拒绝 SO_MARK、TUN 时，流量不会被真正接管。这一版没有在具备这些权限的机器上证明 redirect、tproxy 或虚拟网卡已经接住流量。Windows 的 portproxy 只绑 127.0.0.1。WinDivert 只有 windivert-redirect.c，驱动和 exe 不在包里，选了也不会改系统流量。Android 写出 vpn-session.json，绕过私网、运营商级 NAT、组播和对端地址，包通道在 127.0.0.1:17891，旁边有 LexisVpnService.kt 源码。Termux 不能弹出系统 VPN，也没有编译好的安装包。

SOCKS、HTTP 和固定转发默认只绑 127.0.0.1。只有 link.allowLan 为 true 时才按配置里的地址监听。反向入口同样受这道限制。隧道入口可以听更宽的地址。
出口拨号前会先解析域名。回环、内网、链路本地、运营商级 NAT 和文档地址默认拒绝。egress.allow 一行一个主机、主机:端口或 IPv4 网段，用来单独放行。这道拦截不作用于你本机 SOCKS 的直连和绕行，也不作用于你自己暴露的本机服务。公网的 22、80、443 不单独封禁。握手超时、拨号超时和同时握手数在 link.handshakeMs、link.dialMs、link.maxHandshakes。半开握手上限：link.maxHalfOpen（全局，默认 512）；link.maxHalfOpenPerIp（每网段，默认 8，网段长度 link.halfOpenPrefixV4 默认 24、link.halfOpenPrefixV6 默认 64，设成 32/128 即按单个地址计）。hello 校验失败会立刻让出名额，但连接仍静默保持到握手超时再断开；连上后 link.firstByteMs（默认 2000 毫秒，0 为关闭）内一个字节都没收到也会让出名额，之后到的数据一律忽略；这类静默连接最多 link.maxSilent 条（默认 1024），超过后多出来的会提前断开。半开中的连接也占 link.maxConns（默认 1024），所以 maxConns 要不小于 maxHalfOpen 加上平时的会话数，否则半开上限实际被 maxConns 截住；旧配置里写死 maxConns: 128 的，升级后请改大，进程启动时会提示。

程序名：接入、绕行或拒绝。Linux 从 /proc 认进程，Windows 用当前连接的进程名，Android 上认不到进程时规则仍留在配置里。
路由：DOMAIN、DOMAIN-SUFFIX、IP-CIDR、GEOSITE、GEOIP、PROCESS-NAME、MATCH。内置 geosite/geoip 是一份小样。完整库把文本 URL 填进配置，客户端启动时拉取。域名还不会先解析再套 IP 规则。没有单独的 DNS 入站。假地址只在系统接管里由本机 DNS 服务回答，见上面。

安装：
- Windows：在解压目录里运行 install.ps1。登录后任务 LexisAgent 会把进程拉起。证书只有你自己放进来时才会复制。配置、封存、口令和 TLS 私钥会收成当前用户可读写、别人不可读。
- Linux：sh install.sh。有 systemd 就装用户服务，没有就 nohup。上述文件设为 600。
- Android：在 Termux 里 sh install.sh。同样把这些文件收成仅本人可读。
常驻进程启动时会再收一次。手动覆盖之后重启进程。

状态页默认是 http://127.0.0.1:17890/ ，同端口还有 /health 和 /metrics。
镜像说明在 Dockerfile，样例配置的口令是空的，进程会拒绝启动，要先用 node lexis-agent.mjs --gen-token 生成一个 128 bit 口令填进去再跑。
控制台导出的 JSON 覆盖 lexis.config.json。名单和公钥变化会自己重读，旧会话会断开。两端都要把对方公钥放进 peers，并写同一个用 --gen-token 生成的握手口令（不少于 128 bit）。要让对方从本机出去，把那个节点的 exit 打开。没有做过连续 24 小时的浸泡。

3.0.3：虚拟网卡按流排队。同一条流（协议和两端地址）里的包仍按顺序处理；不同的流互不等待，所以一条慢的拨号不会卡住整张网卡。单条流排队超过 64 个包时丢掉后来的，记在 lexis_tun_flow_drops（TCP 靠对端重传，UDP 可能丢）。整段排队或正在处理的包超过 256 个时，读网卡会先停一下。单个包处理超过 link.dialMs 加 2 秒只记 lexis_tun_stalls，不会插队。发往对端地址的包如果掉进虚拟网卡（到对端的路由没了），直接丢掉，记 lexis_tun_loop_drops；脚本里还给对端地址加了不可达规则，避免隧道套自己。会话正在重连时，UDP 打开最多等 3 秒再试一次，记 lexis_udp_rebuild_retries。套接字上的异步错误和未处理的拒绝不再把进程打崩，未处理的记 lexis_unhandled。这些都没有在真机上证明虚拟网卡已经接住流量。

tun 上传方向（release/3.0-upload）：配置里的 tun 一节。
- tun.mtu（默认 1500；Android 缺省时用 android.mtu）：SYN|ACK 里宣告 MSS = mtu − 40。tun.mss 可以直接指定，优先于 mtu。每条流发送用 min(本端 MSS, 对端 SYN 的 MSS)，对端 SYN 没带 MSS 选项时按 RFC 9293 的 536。
- 乱序缓存：tun.oooMaxBytes（默认 65535，单条流字节上限，不会超过固定的 65535 接收窗口）、tun.oooMaxSegs（默认 64，单条流段数上限，相邻连续段合并后计数）、tun.oooTotalBytes（默认 8388608，整台引擎的总字节上限）。任一为 0 表示不缓存乱序段（只收按序段）。
- 规则：与已收数据重叠的重传只取新的尾部；与缓存段重叠时保留已缓存的字节，只补空隙；超出 rcvNxt + 65535 窗口的部分丢弃；超上限时先丢离 rcvNxt 最远的段（补洞最需要的是近的段，远的段对端会重发）；空洞补上后按序交付并释放；收到 FIN、RST、重置或流被回收时整条流的缓存立即释放。
- 不做窗口缩放：接收窗口固定 65535。窗口缩放要求我们按实际可缓存量宣告窗口，并对 socket.write 做背压，否则放大窗口只会放大内存占用。1 MiB 上传在 65535 窗口、1460 段长下，窗口本身不再是卡住的原因。高 RTT 下吞吐仍受 65535/RTT 限制。
- 重发：未确认的段有超时计时器，起始 1 秒，有往返样本后按 RFC 6298 调整（下限 200 毫秒，上限 60 秒）。超时只重发最早的一段，间隔加倍，直到有新的往返样本。三个纯重复确认，并且最早那段已经比往返时间更老，会提前重发这一段，不等超时。连续 7 次超时且 3 分钟没有确认前进，才发 RST 并关掉这条流和上游连接。RST 的序号是对端还没确认的起点（对端下一期望字节），不是已经发出但还没被确认的数据或 FIN 的末端；若对端的 ACK 落在我们实际发出的序号区间里，会按那个序号再发一次。比较按 32 位回绕。重传不推进这个起点。SYN|ACK 重发过且没有往返样本时，后面的数据从 3 秒起算。这是用户态栈自己的重发，不是系统 TCP。没有在真机上证明虚拟网卡已经接住流量。
